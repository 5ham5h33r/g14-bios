# UEFI code and library changes

I imported the changed PE executables into Ghidra 12.2, exported recovered functions and compared the results against Capstone disassembly. The RVAs below refer to the **decompressed module body**, not the ASUS capsule.

## LIB-01: delta-CRL validation

**Confirmed code; upstream patch match.** ASUS adds a check for a missing CRL Number before passing it to an ASN.1 integer comparison.

The null check appears inside a routine that selects a certificate revocation list and an optional delta CRL. Its structure matches OpenSSL's `get_crl_sk()` with inlined delta-CRL checks. In `TlsDxe`, the relevant recovered routine starts at RVA **`0x347A0`** in both versions.

```text
310:
    compare(delta->crl_number, base->crl_number)

312:
    if (delta->crl_number != NULL)
        compare(delta->crl_number, base->crl_number)
```

In 312, RVA `0x34A96` loads the pointer from `+0x98`; `0x34A9D` tests it, and the conditional branch at `0x34AA0` skips the comparison for null. The following comparison preserves the original ordering test.

This matches OpenSSL commit [59c3b3158553ab53275bbbccca5cb305d591cf2e](https://github.com/openssl/openssl/commit/59c3b3158553ab53275bbbccca5cb305d591cf2e), the fix for **CVE-2026-28388**. I also checked the null guard in four firmware-update variants:

| Module | File GUID | New guard RVA |
|---|---|---|
| TlsDxe | `3ACEB0C0-3C72-11E4-9A56-74D435052646` | `0x34A96` |
| FmpDxe 0 | `BAA122FC-FF0C-3F81-BB19-D1DF8C2B3986` | `0x751A` |
| FmpDxe 1 | `6B21A708-2A77-427D-85E1-9CEB82A52129` | `0x8E76` |
| FmpDxe 2 | `446DF109-83BF-44DB-A86D-8E4B24B954A9` | `0x71AA` |
| FmpDxe 3 | `5035966B-1B4B-4722-9947-654F985C32C3` | `0x732A` |

The [patch-match record](../data/310-312/security-patch-matches.json) includes module hashes, routine entries, guard bytes and upstream commit IDs. The guard pattern is absent from the matching old routine and appears once in each new routine; the count is scoped to that routine, not the whole module.

The patch match establishes the missing check's addition. I have not established that ASUS enables delta-CRL verification in a reachable firmware flow.

## LIB-02: DANE certificate ownership

**Confirmed code; upstream patch match.** The old code frees the cached certificate through the general allocation-free path. The new code uses the certificate-free path and retains the incoming certificate before replacing the cached pointer.

In `TlsDxe`, the old routine starts at **`0x363D4`** and the new one at **`0x363D8`**. The routine's TLSA matching, selector/digest handling and stored match depth identify OpenSSL's `dane_match()` behavior.

The old tail:

```text
Record match depth and TLSA entry.
Free the cached pointer with the general allocator.
Store the incoming certificate.
Increment its reference count.
```

The new tail retains the incoming certificate, checks that operation, frees the previous cached certificate through the X.509 path, and updates the cache. This also changes register allocation in the surrounding routine.

OpenSSL's [ec03fa050b3346997ed9c5fef3d0e16ad7db8177](https://github.com/openssl/openssl/commit/ec03fa050b3346997ed9c5fef3d0e16ad7db8177) replaces the general free with `X509_free()` for this field. OpenSSL associates the repair with **CVE-2026-28387** in its [April 7 advisory](https://openssl-library.org/news/secadv/20260407.txt).

I can identify the repair in the compiled firmware. I cannot infer a complete OpenSSL version from it, and I have not shown a reachable DANE client configuration in the BIOS.

## UI-01: setup interface

**Confirmed code; unresolved presentation effect.** AMITSE's unpacked executable grows by 96 bytes, from 2,658,688 to 2,658,784. Much of the byte difference comes from function and data placement.

One matched child-control construction routine grows from **1,901 to 2,001 recovered body bytes**:

| Version | Routine RVA |
|---|---|
| 310 | `0x124920` |
| 312 | `0x10C0D4` |

In 312, the routine:

- Allocates a child object with `0x4D0` bytes where 310 used `0x4C8`.
- Copies additional nonzero properties from parent offsets `+0x374` and `+0x37C` to each child.
- Copies a parent value from `+0x4F0` into an associated object's `+0x20` field, then calls its update method.

The routine uses layout/control objects and virtual-method calls. I infer a setup-interface property/layout fix. I do not have names for these fields or a screenshot comparison.

The string boundary near `$SETUPPASSWDANY` also changes. A string extraction can expose a different boundary without proving a changed password rule. I have not established a password-security fix, a new setup option or a new password restriction from that marker.

Ghidra recovered 3,065 functions in 310 and 3,064 in 312 for this import. Those counts include shared-tail and boundary errors. The heuristic comparison leaves candidate functions for review; see [coverage](coverage.md).

## Early-boot TE images

The first raw comparison suggested broad changes to `AmdSocFp8StxKrkPei` and the volume-top code. Checking the TE headers and section payloads resolved those differences:

| Module/section | Address words shifted by eight bytes | Bytes still different after that adjustment |
|---|---:|---:|
| `AmdSocFp8StxKrkPei` `.text` | 205 | 0 |
| `AmdSocFp8StxKrkPei` `.data` | 77 | 0 |
| Volume-top `.text` | 342 | 0 |
| Volume-top `STARTUP_` | 4 | 0 |
| Volume-top `.data` | 55 | 0 |

The SoC module's load address shifts from `0x09AE87B0` to `0x09AE87A8`. Its text/data/relocation section sizes stay the same. `PrjPei` text and data match even without an address adjustment.

For the adjustment, I changed a new-image word only where the old value lies within `0x09A00000`–`0x09FFFFFF` and the old/new difference equals eight. I recorded counts and remaining differences in [te-rebase.json](../data/310-312/te-rebase.json). This is a targeted check for this pair, not a general TE equivalence algorithm.

## Date/time, version checks and metadata

`SbRun` and `SbRunSmm` change their embedded fallback date from the 2025 build to the 2026 build. Their date-read code also changes register allocation. The observed sequence still converts a packed decimal value and stores the same resulting field. I have not established a functional RTC repair from it.

`AsusSMBIOS` changes a version digit. `ReFlash` changes two encoded version checks from 310 to 312. Other metadata stores the new build date/time. `PrjDxe` contains a different build-source path and small reference changes; I have not identified a separate behavior change there.

Many small SMM and DXE drivers have matching section payloads after accounting for PE-header placement. The byte-level inventory retains those files so a reader can distinguish a rebuilt wrapper from changed code.
