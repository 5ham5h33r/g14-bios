# Embedded controller: 310 → 312

The EC application changes from `03.10F` to `03.12F`. I used RV32IMC disassembly and a Ghidra import with code at zero and RAM at `0x00800000`.

For this image, add **`0x81800`** to an EC code address to get its capsule-file offset. The board string starts at capsule offset `0x897A0`; the version string starts at `0x897C0`.

## EC-01: battery-care latch

**Confirmed code.** New code uses bit 7 of RAM byte `0x00800370` to remember reaching the upper charge threshold.

| Value | Address or source |
|---|---|
| Relative state of charge | RAM `0x00800755` |
| Battery-care flags | RAM `0x00800370` |
| Battery-care enable | Bit 0, exposed as `BCME` in the DSDT |
| New upper-threshold latch | Bit 7 |
| Stored lower threshold | RAM `0x0080037A` |
| Initial lower threshold in the examined path | `0x4E`, or 78 |
| Upper comparison | `charge > 0x4F`, or charge ≥80 |

The charge byte comes from a Smart Battery read: address `0x16` in 8-bit SMBus notation, command `0x0D`, followed by a store to `0x00800755`. I checked that sequence at capsule offsets `0x946E4`–`0x9475C` in 312. The Smart Battery command identifies relative state of charge.

The new routine at **EC `0x15C64` / capsule `0x97464`**:

```c
/* Original pseudocode. Surrounding charger and power-state conditions omitted. */
if (!battery_care_enabled || !(power_flags & 1)) {
    care_flags &= 0x7f;
    return;
}
if (relative_charge >= 80)
    care_flags |= 0x80;
else if (relative_charge <= lower_threshold)
    care_flags &= 0x7f;
```

Selected instructions in 312:

```text
Capsule 0x974A0  lbu   a5, 0x755(a4)     ; relative charge
        0x974A4  addi  a3, zero, 0x4f
        0x974AC  bgeu  a3, a5, ...        ; skip setting when charge <=79
        0x974B4  ori   a5, a5, -0x80     ; set bit 7
        0x97570  lbu   a5, 0x37a(a5)     ; lower threshold
        0x9757C  bltu  a5, a4, ...        ; preserve latch above lower threshold
        0x97584  andi  a5, a5, 0x7f      ; clear latch
```

At EC `0x15C38` / capsule `0x97438`, a new helper returns true when both bit 7 and battery-care bit 0 are set. At EC `0x15C52` / capsule `0x97452`, another helper clears a two-byte transfer buffer.

The old battery-care routine at capsule `0x97400` used direct comparisons against 80 in places where 312 tests the remembered state. The new code also sets the latch when entering the examined care mode with charge already ≥80. It clears the latch when leaving that mode or the relevant power state.

**Inferred effect:** a stop/resume band around the charge limit, including values that pass 80. This does not establish the behavior of a 60% charge limit from G-Helper. The stored threshold can change, and other mode conditions surround this logic.

## EC-02: charging-current writes

**Confirmed code.** ASUS applies the new latch before communicating a requested current to a charger.

At **EC `0x1406E` / capsule `0x9586E`**, the code prepares a two-byte value, selects target address `0x12` and command `0x14`, and performs a write followed by a readback. The new path clears both buffer bytes when the helper from EC-01 returns true. It also clears them under an existing high-bit condition in RAM `0x0080070F`.

```text
Prepare the requested-current buffer.
Apply the existing conversion.
If the existing inhibit condition is set, clear the buffer.
If battery-care mode and the upper-threshold latch are set, clear the buffer.
Write the buffer to the charger and read it back.
```

Other current-write paths gain the same helper call. One appears near capsule `0xB2378`; another appears near `0xB2696`. Their charger path differs, but both new sequences can clear the outgoing current buffer through the same helper.

The [Smart Battery Charger specification](https://www.sbs-forum.org/specs/sbc110.pdf) uses command `0x14` for ChargingCurrent. The observed write supplies zero under the new condition. I infer a request to stop charging; I have not measured charger behavior or tested the readback on hardware.

ASUS also removes the old assignments of target bytes `0x12` and `0x14` near old capsule `0x95C34`. The corresponding new routine starts using the existing state without those assignments. I retain this as a code observation; I have not established a separate user-visible fix from it.

## EC-03: policy after removing AC power

**Confirmed code; inferred performance effect.** ASUS changes a policy reset that the AC-removal path calls.

The caller at **EC `0x32B44` / capsule `0xB4344`** clears bit 0 of RAM `0x00800344`. The DSDT names that bit `ACIN`. After several battery/power updates, the caller invokes **EC `0x2A200` / capsule `0xABA00`**.

In that reset, 310 loads 8; 312 loads 3. The code writes the value to:

```text
0x008008D8  0x008008D9  0x008008DA
0x008008DB  0x008008DC  0x008008DD
```

Two mirrored state values, `0x008008EF` and `0x008008FF`, also receive the new selector value through this routine. The control value `0xD3` and the following helper calls remain.

### Downstream table selection

The routine at EC `0x2737E` indexes an eight-byte row using a selector, then transfers columns 1–4 into RAM `0x008008CC`–`0x008008CF`. Later code clamps those values into `0x008008D2`–`0x008008D5`.

The four tables below match between the releases. ASUS changes their selected starting tier.

| Table address in 312 EC image | Tier 8, columns 1–4 | Tier 3, columns 1–4 |
|---|---|---|
| `0x455BC` | 15, 18, 36, 80 | 25, 31, 62, 80 |
| `0x45604` | 15, 18, 36, 80 | 15, 18, 36, 80 |
| `0x4564C` | 15, 18, 36, 80 | 25, 31, 62, 80 |
| `0x45694` | 23, 27, 56, 100 | 38, 47, 82, 100 |

The matching 310 tables sit `0x160` bytes earlier. The [table evidence](../data/310-312/battery-policy-tables.json) records their full rows and hashes.

At **EC `0x210BE` / capsule `0xA28BE`**, downstream code takes the battery-side values into budget variables and sends them through a command interface after multiplying by 1000. Among the resulting commands, `0x30` uses the first budget, `0x31` the third and `0x32` the second. I have not assigned a vendor name to each budget field in this repo.

Other logic can reduce the budgets or move between tiers. Temperature, sampled ADC values, power source and performance mode also affect selection. The change supports a less restrictive initial policy after unplugging in some paths. It does not prove a steady-state wattage increase. I have not mapped this reset to fan temperature/RPM breakpoints.

## EC-04: status-word transfer removed

**Confirmed code; unresolved effect.** Near old capsule `0xA5944`–`0xA598C`, the EC reads two words from RAM `0x00800B76` and `0x00800B74`, swaps their byte order, and stores them to `0x0080041C` and `0x0080041E`. The matching routine in 312 omits those transfers.

I have not established what the source words represent. The destination words also appear in power/charging-related code. A source-level name or a hardware trace would help distinguish counters from reported status.

## EC-05: additional calls and exit paths

**Confirmed code; unresolved effect.** Two routines that wrote error/status `-6` and returned in 310 now jump to another routine. The changed paths occur near new capsule `0xB3D86` and `0xB3F40`. A power-transition routine also gains a call before its previous exit sequence.

The available decompiler output has shared-tail and parameter-recovery problems in this area. I retain the offsets without assigning a USB-C, sleep or wake fix.

## Notes for the next pass

- Resolve the two removed status transfers and the changed error-path targets.
