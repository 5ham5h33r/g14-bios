# 309 → 310: UEFI and AMD platform changes

Addresses below are RVAs in the extracted PE image unless marked as file offsets. The [coverage JSON](../data/309-310/ghidra-coverage.json) ties each module/version/GUID to its input SHA-256. Full exports remain local; candidate matches retain addresses and matching methods under [function-candidates](../data/309-310/function-candidates).

## CPU-01: core-count controls

ASUS adds `AsusActiveEfficientCoresSyncToAmd`, GUID **`AFD34632-A599-4E8E-AB9A-C88075DA5EF0`**, a 4,928-byte PE body. This file has no matching instance in 309. Ghidra first recovered 11 functions; manual disassembly of event callbacks at `0x7B8` and `0xA00`, plus helper `0xD44`, brings the export to 14. The callbacks supply the evidence below.

### Setup forms

IFRExtractor RS 1.6.1 finds two new questions in `Setup`, GUID `899407D7-99FE-43D8-9A21-79EC328CAC21`:

| Question | File offset in 310 Setup | Variable field | Options | Default |
|---|---|---|---|---|
| `0x165`, Active Performance-cores | `0x12F1E6` | `AsusSetupItemVariable + 0xA4` | All (`0xFF`), 7 through 1 | All |
| `0x166`, Active Efficient-cores | `0x12F29A` | `AsusSetupItemVariable + 0xA5` | All (`0xFF`), 7 through 0 | All |

The performance-core options have maximum-count suppression expressions. For example, the explicit “7” option is suppressed when hidden question `0x163` is less than 8. Both controls sit under `GrayOutIf(question 0x188 == 1)`. The setup browser and platform policy can further affect what an owner sees; no live BIOS-screen check accompanies this comparison.

The two packaged default-store copies change in the same way:

- `Setup`: 158 → 160 bytes, adding fields at `0x9E` and `0x9F` for the maximum-count questions. Their packaged defaults are zero.
- `AsusSetupItemVariable`: 168 → 170 bytes, adding fields at `0xA4` and `0xA5` with `0xFF` defaults before the trailing reserved bytes.

The [setup evidence](../data/309-310/setup-cores.json) includes the question opcode bytes, offsets, defaults and tool-download hash. The 309 forms lack these two titled controls. Their presence is stronger evidence than new strings alone; menu visibility and successful core reconfiguration remain untested.

### Synchronization and ACPI reporting

The new driver's callback at `0x7B8` reads:

| Variable | GUID | Read size |
|---|---|---|
| `Setup` | `EC87D643-EBA4-4BB5-A1E5-3F3E36B20DA9` | `0xA0` |
| `AodCoreInfo` | `5ED15DC0-EDEF-4161-9151-6014C4CC630C` | `0x312` |
| `AsusSetupItemVariable` | `D763220A-8214-4F10-8658-DE40EF1769E1` | `0xAA` |

If either maximum field is zero, the callback derives the two counts from `AodCoreInfo` bytes 4 and 6: `Setup[0x9E] = byte6 - byte4`; `Setup[0x9F] = byte4`. It writes `Setup` back. Another branch sends the selected bytes to configuration protocol GUID `3DDAEF04-53C3-4F37-BC84-A7CCE3B2C823`, method offset `0xC0`, with identifiers `0xA0` and `0xA1`. The `AsusSetupVariableItem` module adds the names `AmdActiveCoreCount` and `AmdActiveSmallCoreCount` alongside its extended variable mapping. The final hardware effect of those writes remains untested.

Callback `0xA00` reads the maximum and selection variables, locates GNVS protocol GUID `61769861-AE63-4DCE-8D48-2DA831A4B53C`, and writes three packed values:

```text
GNVS + 0x3B = 0x10000 | maximum_pair
GNVS + 0x3F = 0x10000 | selected_pair_with_0xFF_replaced_by_maximum
GNVS + 0x43 = 0x10001
```

The DSDT exposes these as `APEM`, `APEC` and `APEN`. The field offsets and new WMI returns agree with the driver, establishing a complete reporting path. See the [ACPI notes](309-310-acpi.md#cpu-reporting-in-the-dsdt).

The BIOS uses performance/efficient terminology on an AMD platform. G-Helper's [current constant definitions](https://github.com/seerge/g-helper/blob/0a1538ac4fb0337f6cf3d64a907acde10c91a3d9/app/AsusACPI.cs) use Intel comments for the shared WMI IDs; those comments do not identify this laptop's CPU architecture or establish that the application exposes these controls on GA403WR.

## USB4-01: router-detection polling

**Module:** `AmdUsb4Dxe`, GUID `051274F4-A724-4732-BE00-82793A3D499A`.

The debug strings identify the examined routine as `DetectRouter`: **309 RVA `0xC55C` → 310 RVA `0xC590`**. In one lane-capability polling path:

| Operation | 309 | 310 |
|---|---|---|
| Timer preparation inside this path | Initializes a router-local timer at router + `0x90`, argument `2,500,000` | Removes that local initialization |
| Delay between unsuccessful polls | Calls delay helper with `100,000` | Removes that call from this loop |
| Expiry test | Router-local timer at router + `0x90` | Timer pointer at host context + `0x8BA` |
| Exit condition | Both observed lane states reach 2, or timer expires | Same lane-state test, different timer context |

The time helpers use ACPI-timer/TSC paths; the arguments are consistent with microsecond intervals, including the old 100 ms delay and 2.5 s local timer. The new duration depends on a platform configuration value, so a shorter total wait cannot be inferred from the removed delay.

The new initialization routine at `0x23A8` allocates **`0xF9` bytes**, up from **`0xD8`**. It initializes a timer at host-data + `0xD8` using a 32-bit configuration value obtained with token `0x333`, then stores that timer pointer in each host context at `+0x8BA`. Timer initialization and expiry helpers are at `0x9280` and `0x9328` in 310.

This supports a shared host-initialization time budget in place of the old local polling budget. The BIOS may perform more closely spaced reads, with remaining time dependent on earlier initialization. This finding concerns a UEFI startup driver. It does not establish that the Windows USB4 stack or Modern Standby receives the same polling change.

Other USB4 differences include moved debug strings, source-line numbers and configuration-token numbering. Those do not each represent an additional USB4 fix. [Function candidates](../data/309-310/function-candidates/AmdUsb4Dxe-051274F4.json).

## MEM-01: SMM-region clearing

**Module:** `AmdCcxZen5Dxe`, GUID `9FB8AC55-D266-4F86-AC43-BF2BA74F5A7A`; routine at RVA **`0x508C`** in both versions.

The routine consumes the SMRAM descriptor HOB with GUID `6DADF1D1-D4CC-4910-BB6E-82B1FD80FF3D`. The GUID and descriptor layout match the [EDK II definition](https://github.com/tianocore/edk2/blob/master/MdePkg/Include/Guid/SmramMemoryReserve.h). It copies descriptors, sums their sizes and uses the first region's base when programming SMM address/mask registers.

Version 310 inserts this operation before programming the final base/mask:

```text
saved_mask = read_msr(0xC0010113)
write_msr(0xC0010113, read_msr(0xC0010113) & ~3)
if total_size != 0:
    zero_memory(first_region_base, total_size)
write_msr(0xC0010113, read_msr(0xC0010113) | saved_mask)
```

Key 310 instructions:

| RVA | Operation |
|---|---|
| `0x515B` | Read the SMM mask MSR |
| `0x5170` | Clear its low two bits |
| `0x517B` | Write the temporary mask |
| `0x5188` | Call the zeroing routine at `0x400` |
| `0x51A2` | Restore the saved mask bits |

The helper at `0x400` writes zero qwords and then trailing zero bytes. It is a memory-clear operation, not an unresolved library call. [Coreboot's AMD register definitions](https://github.com/coreboot/coreboot/blob/206078d6d990d0b7e51b5d87bc27349cb960ead0/src/include/cpu/amd/msr.h) identify `0xC0010112` and `0xC0010113` as the SMM address and mask registers.

Clearing an SMM reservation before using it supports an initialization/hardening interpretation. The code does not identify a particular advisory, prove that old contents were attacker-controlled, or establish the final protection state on running hardware. [Function candidates](../data/309-310/function-candidates/AmdCcxZen5Dxe-9FB8AC55.json).

## NET-01: IPv6 setup buffer

**Module:** `Ip6Dxe`, GUID `5BEDB5CC-D830-4EB2-8742-2D4CC9B54F2C`; routine at RVA **`0xEB1C`** in both versions.

The routine queries IPv6 interface, route, DNS and gateway information, converts address lists to strings, and updates HII form content. Its sequence corresponds to upstream [EDK II `Ip6GetCurrentSetting`](https://github.com/tianocore/edk2/blob/master/NetworkPkg/Ip6Dxe/Ip6ConfigNv.c).

Version 309 supplies a fixed stack area to those conversion paths. Version 310 allocates an initial **`0x1FE` bytes**, checks the first allocation for failure, and grows the buffer when address/route counts or later list sizes require more space. The sizing code uses a 40-character-per-entry calculation. It also frees the allocated string buffer on the reviewed exits.

For example, new instructions beginning at `0xEB64` prepare the initial allocation. The checks at `0xEBA6` onward read the address and route counts, multiply by `0x28`, compare with `0xFF`, and request a larger allocation where necessary. Later list paths compare their required size with the retained capacity.

This is a real change in buffer lifetime and capacity, consistent with avoiding an oversized-list write into a fixed stack buffer. It is not evidence of faster Windows networking. No trigger, reachable exploit, complete error-path audit or matching upstream security commit has been established; this report assigns no CVE. The heuristic matcher left this function unmatched because the rewrite is substantial; the manual pairing uses its callers, query order and form-update operations. [Candidate record](../data/309-310/function-candidates/Ip6Dxe-5BEDB5CC.json).

## AMD component inventory

The AGESA identification string changes at extracted `AmdVersionDxe` file offset `0x3D9`: `StrixKrackanPI-FP8 1.1.0.0a` → `1.1.0.0c`. Its GUID is `29D40F30-E8BF-4803-88A6-4247A29A5318`. [Hashes and string offsets](../data/309-310/agesa.json).

PSPTool 3.7 enumerates **143 distinct nonzero address/size entries** after collapsing repeated directory references to the same range. **80 have identical payloads; 63 change.** Redundant slots and bundled alternatives remain separate. The changed records contain **33 distinct type/old-hash/new-hash combinations**, including containers and configuration data.

The following table groups related entries; it does not claim that all payloads execute on this laptop:

| Entry family | 309 header version | 310 header version |
|---|---|---|
| MP2 | `B.0.0.2F` | `B.0.0.4F` |
| C20 PHY | `0.2.18.0` | `0.2.18.1` |
| MPIO | `0.11.3.F0` | `0.11.6.26` |
| SPI ROM configuration | `0.23.17.36` | `0.23.17.38` |
| MSMU / reduced MSMU | `FE.5D.18.0` | `FC.5D.1.0` |
| ABL0 | `51.16.D0.50` | `55.26.D0.50` |
| SMU off-chip / CCX core initialization, family 1 | `B.5D.4.0` | `B.5D.B.0` |
| SMU off-chip / CCX core initialization, family 2 | `B.65.4.0` | `B.65.C.0` |
| PSP bootloaders, trusted OS and several TEE headers | `0.3E.4.74` | `0.3E.C.74` |

These are PSPTool's header renderings, often hexadecimal, rather than normalized marketing versions. The MSMU value in particular should not be described as a conventional version increase. MP2 grows from 514,992 to 786,432 bytes; MPIO grows from 80,608 to 80,896 bytes. The two raw 14,368-byte CPU microcode types advance to `0B204032` and `0B600032`; PSPTool's wrapped microcode entries include additional headers and occupy 14,880 bytes.

Some TEE entries change only 17 byte positions despite a new header version. A changed header does not establish a rewritten TEE body. Other PSP, SMU and MP2 payloads contain large byte differences. Their internal behavior has not been recovered, and no vulnerability mapping follows from the version numbers alone.

Most changed APCB copies differ at three header positions. One 13,312-byte `APCB_COPY` has 416 differing positions, including body data; its configuration meaning remains unresolved. `ROM_ARMOR_BIOS_NVSTORE` and a pre-memory TEE payload also change. The complete [PSP comparison](../data/309-310/psp-comparison.json) records offsets, lengths, hashes and overlap-difference counts. Offsets in that file are **absolute capsule-file offsets** from PSPTool's reader, including the capsule prefix. Those counts are not semantic edit counts.

PSPTool warns about unfamiliar generation IDs. It provides a useful parsed inventory, not proof of complete coverage or successful disassembly of protected payloads. See [warnings](../data/309-310/psptool-warnings.json).
