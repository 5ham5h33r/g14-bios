# 309 → 310: ACPI changes

The scan found **83 distinct, checksummed DSDT/SSDT templates** beginning at extracted section-body offsets in each image. **76 match byte for byte; seven change.** The scan preserves firmware-file and raw-section instance identities. Several AMD modules contain multiple tables; dropping the raw-section ordinal would merge them and miss changes.

The [table inventories](../data/309-310/acpi/309-tables.json), [310 inventory](../data/309-310/acpi/310-tables.json) and [paired changes](../data/309-310/acpi/changes.json) retain complete hashes, sizes and source identities. Small ASL diffs sit beside them. Tool: iASL 20260408.

These are templates in update packages. Firmware can select alternatives, patch addresses and names, or generate other tables before exposing ACPI to the OS. This report makes no assumption that Windows loads all 83.

## ACPI-01: NVIDIA power-state ordering

**Table:** `OemNv2T`, firmware-file GUID `31A8592D-BFF6-4A00-B4DB-74F1571E879E`.

| Field | 309 | 310 |
|---|---|---|
| Table length | 17,237 | 17,082 |
| SHA-256 | `8d61f5e870ed381b02cb2ad922c64acb8c95c3968acef406c6d825ca34157381` | `b269537a744aeba25eb597693114bf91d0ea6ee4de111a5185e935732c6b6bee` |

Under `\_SB.PCI0.GPP9.PG00`, the `_ON` method moves this operation before acquiring `EC0.MUT1` and checking `M239`:

```text
Acquire EC0.MUT0, timeout 0x2000
EC0.VGAT = 1
Release EC0.MUT0
```

The `_OFF` method does the same with `VGAT = 0`. In 309, these writes occur later, inside an `ECOK` check in a hardware-transition branch, while the outer method holds `MUT1`. Version 310 also removes an `ECOK`-guarded read of `VIUF` from the end of `_OFF`.

The new methods update the requested EC state even when the main state check skips a transition. They also remove these `MUT1 → MUT0` acquisitions from the examined branches. That supports a power-state synchronization or lock-ordering hypothesis. It does not prove that ASUS fixed a deadlock: that requires a conflicting path, the selected table and a reproduction of the stall.

The alternative packaged `Opt2Tabl` template is unchanged and already updates `VGAT` earlier. A machine using that alternative does not receive this particular ASL delta merely because its BIOS version changes to 310. See the [diff](../data/309-310/acpi/SSDT-OemNv2T.diff) and the unchanged-table hashes in the inventories.

## ACPI-02: GPU wait loop

The DSDT's ASUS WMI GPU-control ID `0x00090020` retains this sequence in its enable path:

```text
GPCE = 0
Sleep(2000 ms)
while EC0.NVPS == 1:
    Sleep(100 ms)
EC0.PWMD = 1
```

Both versions have the same loop and surrounding sequence; [the extracted comparison](../data/309-310/acpi/gpu-wait.json) records matching text hashes. No loop counter, elapsed-time exit or alternative error return appears in that block.

In the unchanged `Opt2Tabl` implementation, `PEGP._PS0` sets `NVPS`, performs the power-on work, then clears `NVPS`. The waiting path depends on that shared state. A failure to clear it could keep that call waiting, but its presence does not prove that a particular freeze entered this path.

The separately discussed names `ECLV`, `EEV0`, `TI3S`, `PWCG` and `_L02` do not appear in the decompiled standalone templates examined here. Names and call paths from another ASUS platform cannot establish this model's behavior. This does not rule out similar mechanisms under other names or inside unexamined/generated tables.

## CPU reporting in the DSDT

**Table:** `Notebook` DSDT, GUID `C118F50D-391D-45F4-B3D3-11BC931AA56D`; 66,199 → 66,275 bytes.

ASUS adds three 32-bit fields to the GNVS region and returns them through WMI queries:

| WMI ID | Field | Driver write offset | Meaning supported by the code |
|---|---|---|---|
| `0x001200D2` | `APEC` | GNVS + `0x3F` | Selected/current core-count pair |
| `0x001200D3` | `APEM` | GNVS + `0x3B` | Maximum core-count pair |
| `0x001200D4` | `APEN` | GNVS + `0x43` | Minimum pair, initialized to `0x10001` |

The new `AsusActiveEfficientCoresSyncToAmd` driver writes these fields. The [UEFI notes](309-310-uefi.md#cpu-01-core-count-controls) trace the setup variables and callbacks. Upstream [ASUS WMI definitions](https://github.com/torvalds/linux/blob/d135ab453a7400a34930bdda1ef4bdc8acfac80e/include/linux/platform_data/x86/asus-wmi.h) identify the core-count IDs; G-Helper uses the same IDs, with Intel-oriented comments. The AMD variable consumers in this image establish the device-specific connection.

The DSDT also adds a zero return for query and set handling of ID `0x00130024`; its intended feature remains unresolved. `ATKD.VERS` changes from `0x020B` to `0x0211`. A version return does not identify a driver release or prove compatibility with a particular Windows package.

See the [DSDT diff](../data/309-310/acpi/DSDT-Notebook.diff). The 310 default `dbx` and the later 312 Wi-Fi-country change do not explain these additions.

## ACPI-03: switch removal status

**Table:** `INTGPPC_`, raw section instance in `AmdCpmOemAcpi`; 38,699 → 38,865 bytes.

Two `_RMV` methods change: `\_SB.PCI0.GPP0.SWUS` and `\_SB.PCI0.GPP1.SWUS`. Version 309 returns zero. Version 310 reads two bytes at `DADR + 0x0A` through `RPRM`:

```text
if read16(DADR + 0x0A) == 0x0604:
    return 0
return 1
```

The PCI class/subclass value `0x0604` denotes a PCI-to-PCI bridge. The new branch retains non-removable status for that value and returns removable status otherwise. The exact device topology and Windows hotplug effect need a hardware check. This is an OS-facing removal-status change, not evidence of an LTR-register or sleep-residency fix. [ASL diff](../data/309-310/acpi/SSDT-INTGPPC_.diff).

## ACPI-04: graphics-memory allocation request

Four table variants change the same method: `CPMDFIG1`, `CPMDFIG2`, `CPMDFIG3` and `CPMDFIG4`, in `AmdCpmDisplayFeatureDxe`, GUID `57E9EEE9-EB7D-4453-BBF7-6C138BF06458`.

Their `ATCS` dispatcher calls `ATCA` for function `0x0A`. It packs the input bytes at offsets 2 and 3 into one byte before calling `M232`:

```text
309: packed = ((input[3] & 0x0F) << 4) | (input[2] & 0x0F)
310: packed = ((input[3] & 0x07) << 5) | (input[2] & 0x1F)
```

AMD's upstream [input structure and function definition](https://github.com/torvalds/linux/blob/d135ab453a7400a34930bdda1ef4bdc8acfac80e/drivers/gpu/drm/amd/include/amd_acpi.h) identify `ATCS 0x0A` as setting a UMA allocation size, with a size **index** and a size **type**. That supports interpreting the new encoding as five index bits and three type bits.

The unchanged `CPMCMN.M232` method writes the data byte to `M231 + 1`, then the command byte to `M231`, under a mutex; its debug label identifies it as `CpmTriggerSmi`. The matching `AmdCpmDisplayFeatureSmm` consumer changes with the producer:

| Consumer detail | 309 | 310 |
|---|---|---|
| Module GUID | `30AF4110-A58E-4EF7-8C75-B725939B3B9F` | Same |
| Handler RVA | `0x44A4` | `0x44A4` |
| Index extraction | `value & 0x0F` | `value & 0x1F` |
| Type extraction | `value >> 4` | `value >> 5` |
| Explicit new bound | Absent in this location | Reject index ≥`0x14` with `EFI_INVALID_PARAMETER` |

The instruction checks appear at 310 RVAs `0x44D5`, `0x44E4` and `0x44F7`. The producer/consumer agreement supports a real interface change rather than a disassembler artifact. Index 19 does not mean 19 GiB: the handler uses a lookup table. This finding establishes neither a higher default VRAM reservation nor a new visible VRAM option.

Module hashes and function-pair candidates appear in the [Ghidra coverage](../data/309-310/ghidra-coverage.json) and [SMM candidate record](../data/309-310/function-candidates/AmdCpmDisplayFeatureSmm-30AF4110.json).
